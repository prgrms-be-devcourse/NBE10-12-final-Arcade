# Arcade 초기 인프라 설정 가이드

> 작성일: 2026-09-14 KST  
> 대상: 데브코스 AWS 계정에 Arcade 운영 환경을 처음 생성하거나 재구축하는 운영자  
> 코드 위치: `NBE10-12-final-Arcade`

## 1. 이 가이드가 만드는 것

Terraform으로 다음 AWS 리소스를 만들고, EC2 Instance Connect Endpoint(EICE)를 통해 단일
EC2에 Docker Compose 서비스를 배포한다.

- VPC, 퍼블릭 서브넷, Internet Gateway, route table
- Elastic IP(EIP), Amazon Linux 2023 EC2, 암호화 gp3 루트 볼륨
- EC2와 EICE 보안 그룹, EICE
- 사용자 업로드용 S3 버킷
- EC2 인스턴스 역할과 GitHub Actions 배포 역할
- Nginx, backend, frontend, PostgreSQL, Redis, Prometheus와 exporter 컨테이너

Terraform은 DNS, 운영 환경변수, 컨테이너와 데이터베이스 내용을 관리하지 않는다. 따라서
`Terraform 적용 → DNS 연결 → 운영 환경 파일 준비 → 최초 배포·복원 → GitHub CD 연결` 순서를
지켜야 한다.

## 2. 시작 전 준비

### 로컬 도구

- AWS CLI v2
- Terraform 1.9 이상
- Git과 GitHub CLI(`gh`)
- Docker와 Docker Buildx
- OpenSSH의 `ssh`, `scp`, `ssh-keygen`
- `curl`, `jq`, `tar`

버전과 로그인을 확인한다.

```bash
aws --version
terraform version
docker version
docker buildx version
gh auth status
aws sts get-caller-identity
```

`aws sts get-caller-identity`의 `Account`가 적용 대상 데브코스 계정인지 확인한다. Terraform
provider도 `aws_account_id`가 다른 계정이면 적용을 거부하지만, plan 전에 사람이 한 번 더
확인한다.

### 외부 서비스

- HCP Terraform 조직 `arcade-team05`
- `project=arcade` 태그가 등록된 workspace `devcos-team05`
- AWS 계정에 등록된 GitHub OpenID Connect(OIDC) provider
  `https://token.actions.githubusercontent.com`
- GitHub 저장소의 `prod` Environment
- `crewon.cloud` DNS를 수정할 권한
- 비공개 GitHub Container Registry(GHCR) 이미지를 읽을 권한
- 인증서 발급 알림을 받을 이메일 주소
- 재구축이면 이전 서버에서 내려받은 PostgreSQL custom-format dump

HCP Terraform workspace는 이 구성의 상태·잠금·이력을 보관한다. 현재 구성은 로컬에서
plan/apply하는 전제이므로 workspace 실행 모드도 Local인지 확인한다. 개인 계정 검증용
workspace도 같은 태그로 연결할 수 있지만 AWS 계정과 `environment` 입력은 분리한다.

## 3. Terraform 입력 준비

저장소로 이동하고 실제 입력 파일을 만든다.

```bash
cd NBE10-12-final-Arcade/infra/terraform
cp devcos.tfvars.example devcos.tfvars
```

`devcos.tfvars`에서 다음 값을 확인하거나 교체한다.

| 입력 | 정하는 방법 |
| --- | --- |
| `aws_account_id` | `aws sts get-caller-identity --query Account --output text` |
| `team_tag` | 팀 규칙에 맞는 값. Team 05 기본값은 `devcos-team05` |
| `environment` | 데브코스 운영 환경은 `prod`, 개인 계정 검증은 `dev` |
| `region` | 기본값 `ap-northeast-2` |
| `github_repo` | `owner/name` 형식의 실제 저장소 |
| `github_repository_owner_id` | `gh api orgs/<owner> --jq .id` |
| `github_repository_id` | `gh api repos/<owner>/<repo> --jq .id` |
| `deploy_environment` | 워크플로와 같은 `prod` |
| `vpc_cidr`·`public_subnet_cidr` | 기본값 `10.5.0.0/16`, `10.5.1.0/24` |
| `domain` | scheme과 경로를 뺀 루트 도메인 |
| `operator_ssh_public_key` | 운영자 OpenSSH 공개키 한 줄 |
| `app_cidrs` | 공개 서비스이면 `["0.0.0.0/0"]` |
| `ssh_allowed_cidrs` | 기본 `[]`. 직접 SSH가 꼭 필요할 때만 운영자 IPv4 `/32` |
| `s3_bucket_name` | 전체 AWS에서 유일한 소문자 버킷 이름 |

운영자 키가 없다면 만든다. `.pub` 파일만 tfvars에 넣고 개인키는 공유하거나 커밋하지 않는다.

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/arcade-devcos -C "arcade-devcos-operator"
```

`devcos.tfvars`와 개인키는 커밋하지 않는다.

## 4. Terraform 검증과 적용

처음 한 번 HCP Terraform에 로그인하고 초기화한다.

```bash
terraform login app.terraform.io
terraform init
terraform workspace list
terraform workspace select devcos-team05
terraform workspace show
terraform fmt -check
terraform validate
terraform plan -var-file=devcos.tfvars -out=devcos.tfplan
terraform show devcos.tfplan
```

`workspace show` 결과가 `devcos-team05`인지 확인한 다음에만 plan한다. 태그 선택 목록에
workspace가 없다면 HCP Terraform에서 해당 workspace에 `project=arcade` 키·값 태그를
등록하고 다시 `terraform init`한다.

plan에서 다음을 확인한다.

1. provider가 표시한 AWS 계정과 리전이 의도한 값이다.
2. 삭제 또는 예상하지 않은 EC2 교체가 없다.
3. EC2, EIP, EICE, S3와 GitHub Actions 역할이 각각 한 개다.
4. 22번 포트는 EICE 보안 그룹에서만 들어오며, 직접 SSH를 쓰지 않으면 외부에 열리지 않는다.
5. S3 버킷 이름이 충돌하지 않는다.

확인한 plan 파일만 적용한다.

```bash
terraform apply devcos.tfplan
terraform output
```

이후 단계에서 다음 출력값을 사용한다.

```bash
terraform output -raw public_ip
terraform output -raw instance_id
terraform output -raw eice_id
terraform output -raw github_actions_role_arn
terraform output -raw uploads_bucket
terraform output -raw uploads_public_url_prefix
terraform output -raw eice_connect
```

EC2의 cloud-init이 끝났는지도 확인한다.

```bash
$(terraform output -raw eice_connect)
sudo cloud-init status --wait --long
docker version
docker compose version
exit
```

`cloud-init status`가 `done`이 아니면 배포하지 않고 `/var/log/cloud-init-output.log`부터
확인한다.

## 5. DNS 연결

도메인 제공자의 DNS 관리 화면에서 두 A 레코드를 Terraform의 `public_ip`로 지정한다.

| 타입 | 호스트 | 값 |
| --- | --- | --- |
| A | `@` | `terraform output -raw public_ip`의 결과 |
| A | `metrics` | 같은 public IP |

기존 서버를 교체했다면 두 레코드의 이전 IP를 새 EIP로 바꾼다. DNS 전파를 확인한 다음에만
Let's Encrypt 인증서를 발급한다.

```bash
dig +short crewon.cloud A
dig +short metrics.crewon.cloud A
```

두 결과가 모두 새 `public_ip`와 같아야 한다.

## 6. 운영 환경 파일 준비

저장소 루트에서 예시를 복사하고 실제 값은 로컬 파일에만 입력한다.

```bash
cd ../..
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

최소한 다음 묶음을 실제 운영값으로 채운다.

- PostgreSQL, Redis와 PostgreSQL exporter 계정·비밀번호
- 관리자 계정과 JWT secret
- GitHub OAuth 및 GitHub App 값
- `PUBLIC_ORIGIN=https://crewon.cloud`
- S3 설정
  - `CUSTOM__STORAGE__TYPE=s3`
  - `CUSTOM__STORAGE__S3__REGION=ap-northeast-2`
  - `CUSTOM__STORAGE__S3__BUCKET`: Terraform `uploads_bucket` 출력값
  - `CUSTOM__STORAGE__S3__PUBLIC_URL_PREFIX`: Terraform 출력값
  - `CUSTOM__STORAGE__S3__PATH_STYLE_ACCESS=false`
- 메일을 쓰면 `CUSTOM__MAIL__ENABLED`, `CUSTOM__MAIL__FROM`, `RESEND_API_KEY`
- `PROMETHEUS_EXTERNAL_URL=https://metrics.crewon.cloud/prometheus`
- `API_BASE_URL_INTERNAL=http://nginx:8081/api/v1`
- 병렬 프론트 교체를 위한 `FRONTEND_HOST_PORT=0`

Compose 보간과 필수값을 검사하되 환경 파일 내용은 출력하지 않는다.

```bash
docker compose --env-file .env.prod \
  -f docker-compose.yml -f docker-compose.monitoring.yml config --quiet
```

`.env.prod`에는 비밀값이 있으므로 Git에 추가하지 않는다.

## 7. GHCR 이미지 준비

CI가 만든 backend와 frontend 이미지를 사용한다. 태그를 추측하지 말고 GHCR에서 실제 존재를
확인한다. `latest`를 사용할 수 있지만 배포 워크플로는 같은 digest에 연결된 짧은 SHA 태그를
찾아 실행 버전을 기록한다.

비공개 패키지를 수동 배포할 때는 `read:packages` 권한이 있는 classic Personal Access
Token(PAT)을 현재 셸 환경변수로만 제공한다. OAuth scope 이름은 `read:packages`이며
`read:package`가 아니다.

```bash
export GHCR_USER='<GitHub 사용자명>'
read -s GHCR_TOKEN
export GHCR_TOKEN
```

## 8. 최초 배포 또는 새 서버 복구

### 데이터 없이 처음 시작

DNS가 새 EIP를 가리키는 것을 확인한 뒤 실행한다.

```bash
./infra/scripts/eice-deploy.sh "$(cd infra/terraform && terraform output -raw instance_id)" \
  --region ap-northeast-2 \
  --env-file .env.prod \
  --backend-image ghcr.io/prgrms-be-devcourse/nbe10-12-final-arcade/backend:latest \
  --frontend-image ghcr.io/prgrms-be-devcourse/nbe10-12-final-arcade/frontend:latest \
  --certbot-email '<인증서 알림 이메일>'
```

### PostgreSQL dump를 함께 복원

`--restore-confirm`은 실수로 다른 데이터베이스를 지우지 않도록 `.env.prod`의
`POSTGRES_DB`와 같은 이름을 한 번 더 요구하는 확인값이다.

```bash
./infra/scripts/eice-deploy.sh "$(cd infra/terraform && terraform output -raw instance_id)" \
  --region ap-northeast-2 \
  --env-file .env.prod \
  --backend-image ghcr.io/prgrms-be-devcourse/nbe10-12-final-arcade/backend:latest \
  --frontend-image ghcr.io/prgrms-be-devcourse/nbe10-12-final-arcade/frontend:latest \
  --certbot-email '<인증서 알림 이메일>' \
  --restore-dump '<로컬 dump 파일>' \
  --restore-confirm '<POSTGRES_DB 값>'
```

이 명령은 배포 파일·환경 파일·dump를 EICE로 전송하고 다음 작업을 순서대로 수행한다.

1. DNS를 이용해 최초 TLS 인증서를 발급한다.
2. PostgreSQL을 먼저 기동해 dump를 복원한다.
3. PostgreSQL exporter 역할과 비밀번호를 동기화한다.
4. backend와 frontend 후보를 healthy 상태로 만든 뒤 Nginx 대상을 전환한다.
5. Prometheus와 exporter를 기동한다.
6. PostgreSQL 백업을 매일 한국시간 17:55에 실행하고 Certbot 하루 2회 갱신 확인 timer를 등록한다.
7. 원격 임시 묶음과 GHCR 인증정보를 삭제한다.

인증서를 이미 발급한 같은 서버에 일반 재배포할 때는 `--certbot-email`, `--restore-dump`,
`--restore-confirm`을 다시 주지 않는다.

## 9. 최초 배포 검증

### 외부 경로

```bash
curl -fsS https://crewon.cloud/healthz
curl -fsS -o /dev/null 'https://crewon.cloud/api/v1/parties?size=1'
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://metrics.crewon.cloud/prometheus/-/healthy
```

metrics 경로는 Basic Auth를 요구하므로 `401 Unauthorized`가 나오면 외부 인증 경계가 동작한
것이다. 실제 Prometheus 확인은 운영 계정으로 로그인해서 수행한다.

### 서버 내부

Terraform의 `eice_connect` 출력 명령으로 접속해 확인한다.

```bash
cd /opt/arcade
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml --env-file .env ps
systemctl status arcade-backup.timer --no-pager
systemctl status arcade-certbot-renew.timer --no-pager
sudo cloud-init status --long
```

다음을 완료 조건으로 삼는다.

- backend와 frontend가 `healthy`다.
- PostgreSQL과 Redis가 `healthy`다.
- Prometheus, Nginx exporter, PostgreSQL exporter가 실행 중이다.
- HTTPS 인증서 오류 없이 Nginx가 실행 중이다.
- 복원했다면 주요 테이블과 예상 데이터가 존재한다.
- 두 systemd timer가 `enabled`이며 다음 실행 시각이 표시된다.

## 10. GitHub 자동 CD 연결

GitHub 저장소의 `Settings → Environments → prod`에 다음 값을 등록한다. 배포 권한과 운영
비밀값을 production 환경에 한정하기 위해 Environment 단위 등록을 표준으로 사용한다.

### Environment secrets

| 이름 | 값 |
| --- | --- |
| `AWS_ROLE_ARN` | `terraform output -raw github_actions_role_arn` |
| `ENV_PROD` | 로컬 `.env.prod` 파일 전체 내용 |

GitHub CLI로 `ENV_PROD`를 갱신할 때는 값을 화면에 출력하지 않는다.

```bash
gh secret set ENV_PROD --env prod < .env.prod
gh secret set AWS_ROLE_ARN --env prod
```

두 번째 명령은 값을 숨겨 입력받는다. ARN은 계정 ID 숫자만이 아니라
`arn:aws:iam::<계정 ID>:role/arcade-github-actions-role` 전체 문자열이다.

### Environment variables

| 이름 | 값 또는 기본값 |
| --- | --- |
| `AWS_REGION` | `ap-northeast-2` |
| `BACKEND_TAG` | 선택. 없으면 `latest` |
| `FRONTEND_TAG` | 선택. 없으면 `latest` |
| `K6_MAX_DURATION` | 선택. 기본 `10m` |
| `K6_POST_DEPLOY_SECONDS` | 선택. 기본 `10` |
| `K6_RATE` | 선택. 기본 초당 5회 |

```bash
gh variable set AWS_REGION --env prod --body ap-northeast-2
```

CD workflow는 수동 실행 또는 `develop` push에 대한 `CI` 성공 후 실행된다. 첫 자동 배포는
GitHub Actions의 `CD` 실행에서 다음을 확인한다.

- OIDC 역할 인수 성공
- backend와 frontend image digest 및 SHA 태그 출력
- EICE 전송과 서버 배포 성공
- k6의 HTTP 실패율 0, threshold 성공, 예상 backend 버전 관찰
- `/healthz`와 API smoke test 성공

## 11. 백업과 재구축 준비

서버의 `arcade-backup.timer`가 만든 최신 PostgreSQL dump를 주기적으로 로컬에 내려받는다.
`--create`를 주면 서버의 `arcade-backup.service`를 먼저 실행해 새 dump를 만든 뒤 그 파일을
바로 내려받는다. 인스턴스 ID를 직접 주면 스크립트의 Name 태그 기본값과 무관하게 정확한 서버를
선택한다.

```bash
./infra/scripts/eice-download-backup.sh \
  "$(cd infra/terraform && terraform output -raw instance_id)" \
  --create \
  --region ap-northeast-2 \
  --output-dir backups/postgres
```

스크립트는 원격과 로컬 파일의 SHA-256을 비교하고 로컬 dump를 mode `600`으로 저장한다.
정기 백업은 데브코스 EC2의 18시 자동 중지 전에 시작하도록 17:55 KST로 고정한다.
EC2의 루트 EBS도 Terraform destroy 대상이므로 destroy 전에 이 사본이 실제로 존재하는지
반드시 확인한다. Redis 세션과 Prometheus 시계열은 현재 복구 대상이 아니다.

## 12. 제거 절차

제거 전에 PostgreSQL dump를 내려받고 S3 사용자 업로드 보존 방침을 확인한다. 그다음 현재
상태를 기준으로 destroy plan을 만들고 검토한 파일만 적용한다.

```bash
cd infra/terraform
terraform plan -destroy -var-file=devcos.tfvars -out=destroy.tfplan
terraform show destroy.tfplan
terraform apply destroy.tfplan
```

destroy 후에는 다음 외부 상태를 별도로 정리하거나 갱신한다.

- 도메인의 A 레코드
- GitHub `prod` Environment의 `AWS_ROLE_ARN`
- 로컬에 남긴 `devcos.tfvars`, `.env.prod`, dump
- HCP Terraform workspace의 상태·실행 이력 보존 여부

## 자주 막히는 지점

| 증상 | 먼저 확인할 것 | 조치 |
| --- | --- | --- |
| Terraform이 OIDC provider를 못 찾음 | AWS IAM의 `token.actions.githubusercontent.com` provider | 이 코드는 provider를 생성하지 않고 조회한다. 공유 계정 관리자에게 등록을 요청한다. |
| GitHub Actions OIDC 역할 인수 실패 | `prod` Environment, 저장소 owner/repository 숫자 ID, `AWS_ROLE_ARN` 전체 값 | tfvars와 실제 저장소·Environment를 일치시킨 뒤 plan/apply하고 Secret을 갱신한다. |
| GHCR inspect 또는 pull이 `403` | PAT scope와 패키지 접근 권한 | classic PAT에 `read:packages`를 부여한다. 잘못된 `read:package` scope는 사용하지 않는다. |
| Nginx가 인증서 파일 부재로 반복 종료 | DNS 전파와 `data/certbot/conf/live/<domain>` | Nginx 기동 전에 최초 복구 명령에 `--certbot-email`을 포함해 인증서를 발급한다. |
| PostgreSQL exporter 인증 실패 | `.env.prod`의 exporter 비밀번호와 DB 역할 비밀번호 | 배포 스크립트를 다시 실행해 역할을 동기화하고 exporter를 재생성한다. |
| cloud-init `Unknown user or group: ec2-user` | `cloud-init status --long`, cloud-init 출력 로그 | 현재 템플릿은 사용자 생성 뒤 키를 설치한다. 이전 템플릿으로 만든 인스턴스면 수정된 Terraform으로 재생성한다. |
| backend가 `CannotCreateTransactionException` | Hikari active/idle, PostgreSQL 세션과 장기 transaction | 단순 재배포로 단정하지 말고 connection pool 고갈 원인을 로그·Prometheus에서 확인한다. |
| backend가 schema validation에서 기동 실패 | 배포 버전이 요구하는 DDL과 복원 dump schema | 배포 전에 승인된 SQL을 적용한다. 현재 Flyway가 없으므로 schema 변경은 자동 복원되지 않는다. |
